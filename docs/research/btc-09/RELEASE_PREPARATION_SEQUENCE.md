# BTC-09 — Exact release preparation sequence (for a FUTURE, separately authorized release)

Nothing here is executed. Every step that changes production state needs Project Control's explicit authorization (D07 for steps 4–6, D08 for 7–9). Defaults stay `BTC_APPROVED_COMPOSITE_SHA256=[]`, `ARTIFACT_RECORDS=()` until step 6.

0. Preconditions: amendment PC-BTC09-A1 approved; D05 restore recorded; the release id, decision ref and rights ref chosen; artifact 12524137867 expires 2026-10-24T18:51Z, after which the owner TAR is the only build input (restore it with `tools/btc_07b_package restore` at commit `641151b9…` in a private environment).
1. Source snapshot: verify TAR SHA-256 = `19abaa9b…d4ce`; restore; snapshot id must be `btc04e-e11c2538168b2bde`; replay IDENTICAL.
2. Calculation commit C: the main commit that will not change before the release commit R except for the registry/pin/public-data lines (see 6). Record C.
3. Candidate rebuild at C (private): run `tools/btc_09_preflight.py` (or the manual BTC-09 workflow with its checkout at C) with `GITHUB_SHA=C`. Required: `ok: true`; sidecar SHA-256 still `a0bcb9bad3c093033beba741ddd1fed3ad5626f5f1483beb87efb68518c8ba8a`; 0 value differences; candidate SHA-256 recorded (it is commit-bound).
4. Artifact identity (private): `compose_release` with the chosen release id → composite bytes → composite SHA-256 (= public payload SHA-256). `record_template` with `bc.private_hashes(preview, sidecar)` → template with `owner_approval=PENDING`.
5. Mandatory `release_preflight(composite, record, preview_bytes, sidecar_bytes, previous_public_bytes)` on the private inputs, with the owner-approved record (APPROVED, approver, date): must return the record. A template or any failing negative case blocks the release.
6. Release change set (one PR, created only after D07/D08 authorization; a branch push triggers a public Cloudflare preview, so no release-branch push before authorization): (a) the record into `ARTIFACT_RECORDS` (`etl/btc_contract.py`), (b) the composite SHA-256 into `BTC_APPROVED_COMPOSITE_SHA256` (`frontend/src/btc.ts`), (c) the composite bytes as `frontend/public/data/monthly.json` via `etl/btc_release.py export_composite`. Verify with `python -m tools.btc_10_changeset_check --calc-commit C --baseline-commit B --release-commit R --record RECORD.json` (three-commit model; B = main after the BTC-10 PR; see docs/research/btc-10/D07_RELEASE_CHANGESET_CHECK.md) that R differs from B only in these three locations, docs and tests, and that the calculation code of B equals C. Run the full suite, `etl.data_quality`, browser acceptance with the real composite, and `tools/btc_09_distribution_check.py` (which then must be run knowing the JSON intentionally differs from the legacy file).
7. Deployment: merge only on explicit authorization; Cloudflare Pages deploys the static build. Record deployment id, commit R, live JSON SHA-256.
8. Cache validation in the deployment window: `curl -sI` the JSON and the main JS from two locations (record `cache-control`, `etag`, `age`); body SHA-256 of the live JSON must equal the record's `public_payload_sha256`; the served JS must contain that pin; clean-profile and hard-reload checks must agree; purge and repeat if an old etag is served. A stale JSON or JS can only hide Bitcoin, never show unauthorized data.
9. Rollback (see ROLLBACK_RUNBOOK.md): redeploy the previous Pages deployment or revert R; validate with `tools/btc_09_distribution_check.py state` (legacy sha `1afb0bf9…91d8cd`, no Bitcoin keys, empty pins), clean-profile browser check, cache check, `bc.rollback_target_ok`.
