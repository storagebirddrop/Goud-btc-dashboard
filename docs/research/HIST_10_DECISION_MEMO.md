## 2. Provisional assumptions (research use only, may be revised)

* 50% calendar-day threshold for a monthly FX mean (decision 7); with it no 1971-1998 or 1999-2026 month was dropped except the partial final month 2026-10 (21 days observed, rule-based null).
* "Partial final month" means: a Monday-Friday still lies after the last observation inside that month. A month that ends on a TARGET holiday would therefore be treated as partial; this fails closed and only affects the last month of a series.
* Quality levels A/B/E and their rounding bounds are the HIST-08 PROPOSED thresholds, not a measured accuracy guarantee; World Bank gold is whole USD (rounding up to 0.45% in 1975-1978, 0.22% worst case 1979-1998).
* Source windows used for the vintage pins (World Bank 1975-01..2026-08, Fed 1971-01-04..1998-12-31, ECB 1999-01-04..2026-08-31) were chosen to match what the research results depend on.

## 5. Source-vintage reproducibility (assessment and smallest governance-consistent solution)

What is **proven**: the same downloaded bytes always produce the same bundles (offline tests; real-data rebuild identical in one job). That is **code determinism only**. It does not show that the historical sources are unchanged: the World Bank workbook is replaced monthly, the ECB daily file grows daily, and bundle bytes contain the acquisition timestamp, so bundle hashes differ between runs.

What is **implemented now** (all without committing restricted raw data): every observation records its exact source identifier, source file sha256, vintage and the actual UTC acquisition time; every point carries the method flag `METHOD:HIST10_M1_V1`, the quality-level flag and the rule flag; a manifest (`summary.json`, key `manifest`, and `hist10_manifest.json`) records method id, source ids and hashes, acquisition time, bundle hashes and the quality-flag table; `data/fixtures/hist10/source_pins.json` pins, per source, a **window hash** (canonical `key:value` lines up to a cutoff, so appended data does not disturb it but a revision inside the window does) plus a hash of the derived half-year values. Each run reports `vintage_check`: `MATCH` (the pinned research result is reproduced), `SOURCE_REVISED` (a pinned source window differs: this run is not the pinned result), `DEFECT_DERIVED_DRIFT` (sources equal but values differ: a code or method defect), `METHOD_CHANGED`, `UNPINNED`.

What it **cannot** do: reproduce a revised source's old bytes. Smallest further step, for Project Control to decide with the rights question: (1) keep the pins in Git and treat every `SOURCE_REVISED` as a human-reviewed event that produces a new, versioned pin file (old pins stay in Git history); (2) if exact reproducibility is required, retain the raw bytes of each vintage in an owner-controlled private store outside Git and outside public artifacts, with an index (source id, sha256, acquisition time, URL) committed in Git, only after the rights assessment of decision 9; (3) where a publisher offers vintages (for example archived data releases) record that vintage identifier in the manifest; availability is UNVERIFIED. Workflow artifacts (14 days) are not a vintage archive.
